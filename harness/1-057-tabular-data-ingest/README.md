# Harness — 1.057 Tabular Data Ingest

Everything the survey's S2 numbers came from. Nothing here is committed as data: the
fixtures are generated and the venv is rebuilt, so a re-run reproduces the inputs rather
than trusting a checked-in copy of them.

## Rebuild and re-run

```bash
uv venv --python 3.12 .venv
VIRTUAL_ENV=.venv uv pip install \
  "pandas==3.0.5" "polars==1.44.2" "duckdb==1.5.5" "openpyxl==3.1.5" \
  "python-calamine==0.8.2" "pandera==0.33.1" "pydantic==2.13.5" \
  "xlsxwriter==3.2.9" "petl==1.7.25" "pyarrow==25.0.1"

.venv/bin/python gen_fixtures.py --rows 10000
.venv/bin/python l1_install.py        # install closure, dependencies, cold import
.venv/bin/python l2_correctness.py    # the hazard matrix — the headline
.venv/bin/python l3_throughput.py     # wall time and peak RSS at 10k / 100k / 1M
.venv/bin/python l4_spreadsheet.py    # openpyxl vs calamine, direct and via pandas
.venv/bin/python l5_errors.py         # which rows failed, and whether the reason is usable
```

`l1_install.py` builds one throwaway venv per library, so it takes a few minutes and needs
`uv` on PATH.

## What is where

| | |
|---|---|
| `gen_fixtures.py` | the fixture generator, and `HAZARDS` is **the answer key** L2 scores against. The `notes` sheet is created BEFORE `data` on purpose, so sheet index 0 is the wrong sheet |
| `l1`–`l5` | one script per measurement level, matching the survey's `measurement-plan.md` |
| `results/*.json` | raw output, regenerated by the scripts above |
| `results/machine.json` | the machine, the kernel, the interpreter and every pinned version |
| `registry-2026-09-09.json` | the PyPI / GitHub / pypistats snapshot every S1 figure was read from |

## Reading the numbers

**They may be compared with each other and with nothing else.** Measured on aarch64 under
WSL2. polars, DuckDB, calamine and pyarrow are compiled; the stdlib module, petl and much
of pandas are interpreted CPython, and a compiled-against-interpreted ratio on aarch64 does
not share an axis with one measured on x86_64. The x86 arm is L7 in the measurement plan
and did not run.

Wall time is the minimum of five rounds (three at 1M rows) inside a fresh subprocess per
reader, so peak RSS belongs to that reader alone.

## The leveling check

L3 asserts every reader returned identical row counts and identical checksums before any
timing is compared, prints `identical work across readers: True`, and records the verdict
under `fair` in the results file alongside `rounds_per_size`. If that line ever
reads `False`, the timings below it mean nothing — a reader doing less work is not a faster
reader.
