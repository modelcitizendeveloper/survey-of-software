# 1.047 Caching Libraries

Python caching: redis-py, pymemcache, diskcache, cachetools — and Redis vs Valkey behind the client. The tier decides before the library.

## At a glance


- **redis-py** — The distributed default — proven at scale, and the reason it wins is rarely caching alone but the data structures, pub/sub and persistence that come with it. Talks to Redis and Valkey unchanged.
- **Valkey (server; clients redis-py, valkey-glide, valkey-py)** — The BSD-licensed, Linux Foundation fork of Redis 7.2. Wire-compatible, so the client code does not change; the choice is a licence and procurement decision, and it is one-way — Valkey reads Redis 7.2 data files, not Redis 7.4+ ones.
- **pymemcache** — The fastest option when you want a cache and nothing else. Minimal overhead, no feature surface to grow into — chosen when Redis's extras are not wanted.
- **diskcache** — SQLite-backed local persistence with no server to run. The answer for a cache that must survive a restart on a single machine.
- **cachetools** — In-process decorators with LRU/TTL policies, in a standard-library idiom. The right first reach before any infrastructure exists.


**What the research found**

- The decision is the tier, not the library: in-process, local-persistent and distributed are three different problems, and within each tier the choice is nearly settled
- Redis wins the distributed tier on things that are not caching — memcached is faster at the narrow job, and teams still pick Redis for the surrounding capabilities
- diskcache occupies a gap teams usually fill badly: persistent caching on one machine, where the alternatives are a server you did not need or a cache you lose on restart
- cachetools is where most caching should start; reaching for a cache server before exhausting in-process memoization is the category's common over-engineering
- Since 2024 the distributed tier has two servers, not one: Redis (RSALv2 / SSPLv1 / AGPLv3 from 8.0) and Valkey (BSD-3-Clause). redis-py speaks to both, so the server can be chosen on licence and hosting price — but only while the data is still on Redis 7.2 or older

**Simple Definition**: Software tools that temporarily store frequently accessed data in fast-access memory to reduce expensive database queries and API calls.

## The server behind redis-py: Redis or Valkey (added 2026-08-20)

The distributed tier used to mean one server. Since March 2024 it means two, and the
Python client does not care which — so the choice moved out of this survey's usual
criteria (speed, features) and into licence, hosting price and data-file compatibility.

**What happened, in order** (dates from the projects' own licence and release pages):

| Date | Event |
|---|---|
| 2024-03 | Redis Inc. moves Redis 7.4 from BSD-3-Clause to RSALv2 / SSPLv1 (source-available, not OSI-approved) |
| 2024-03-22 | Linux Foundation launches **Valkey**, a fork of Redis 7.2.4, BSD-3-Clause; launch backers AWS, Google, Oracle, Ericsson, Alibaba, Huawei, Tencent |
| 2024-10-08 | AWS ships ElastiCache and MemoryDB for Valkey, priced 20% below Redis OSS node-based and 33% below serverless |
| 2025-05-01 | Redis 8.0 adds **AGPLv3** as a third option (RSALv2 / SSPLv1 / AGPLv3); Redis says it plans to keep that configuration |
| 2025-10-21 | Valkey 9.0 GA: numbered databases in cluster mode, atomic slot migration, hash-field expiry (HEXPIRE), `>1` billion req/s on a 2,000-node cluster |
| 2026-05-19 | Valkey 9.1: 2.1 M req/s on one server, up to 20% less memory for short strings, database-level ACLs |
| 2026-07-21 / 2026-08-17 | Current patch lines: Valkey 9.1.1 · Redis 8.10.1 |

**Valkey at a glance** (GitHub API, 2026-08-20): 26.9k stars, 1.3k forks, BSD-3-Clause,
`valkey-io/valkey`. Google Memorystore for Valkey supports 7.2, 8.0 and 9.0 (9.1 in
preview); Aiven and DigitalOcean offer it too.

**What stays the same.** Valkey speaks RESP2 and RESP3 and reports `redis_version:7.2.4`
in `INFO`; `redis-py` connects without code changes. Install symlinks `redis-server` and
`redis-cli` to the Valkey binaries. Redis-style config files are accepted. Modules written
against the `RedisModule_` API load.

**What does not.** Valkey reads RDB and AOF files from Redis 7.2 and earlier. RDB files
written by Redis 7.4 and later do not load. So the move is cheap from Redis ≤ 7.2 and a
key-by-key copy over the wire from anything newer — decide before upgrading past 7.2,
not after.

**Three Python clients, not one:**

| Client | Licence | Stars | Latest | Speaks to | Note |
|---|---|---|---|---|---|
| `redis-py` | MIT | 13.6k | 8.1.0 (2026-07-30) | Redis and Valkey | Unchanged; the default stays the default |
| `valkey-glide` | Apache-2.0 | 778 (monorepo) | 2.5.1 (2026-08-11) | Valkey 7.2–9.0, Redis 6.2–**7.2** | Rust core, official Valkey client, AWS- and GCP-backed; async/sync, cluster, OpenTelemetry. Does **not** list Redis 8 |
| `valkey-py` | MIT | 280 | 6.1.1 stable (2025-08-11); 6.2.0rc2 (2026-03) | Valkey and Redis | Fork of redis-py; `import valkey as redis` alias. Moves slowly — a year between stable releases |

**Modules.** Redis 8 bundles the former Redis Stack (JSON, search, time series, Bloom,
vector sets) under the tri-licence. Valkey's equivalents are separate BSD modules:
`valkey-json` 1.0.2 (2025-09), `valkey-bloom` 1.0.1 (2026-02), `valkey-search` 1.1.1
(2026-07, vector search and secondary indexes).

**For this survey's question — which library — nothing changes: `redis-py`.** For the
server behind it:

- **Valkey** when the licence matters (BSD vs AGPL / SSPL policies), when you buy managed
  caching from AWS or GCP (it is the cheaper SKU), or when you are on Redis ≤ 7.2 today.
- **Redis 8** when you want the Stack modules and vector sets from one vendor, or you are
  already on 7.4+ and the data would have to be re-copied to leave.
- **Either**, for a pure cache: the difference is the licence on the box, not the speed of
  `GET`.

Valkey 9.0 (2025-10-21) is where the fork stopped being a re-badge: numbered databases in
cluster mode, atomic slot migration (whole slots moved in AOF form rather than key by key),
per-field hash expiry (`HEXPIRE`, `HTTL`, `HPERSIST`), `DELIFEQ`, polygon geosearch, and
the project's headline number — over one billion requests per second across 2,000 nodes.
9.1 (2026-05-19) reports 2.1 million req/s on a single server (512-byte payloads, 9 I/O
threads, pipeline depth 10), up to 20% less memory for strings under 128 bytes, and ACLs
scoped to a database (`db=`). Redis 8 answered with vector sets (its first new data type in
years) and the bundled Stack modules. On the plain cache path — `GET`, `SET`, `SETEX`,
`EXPIRE`, pipelines, pub/sub — the two are the same server with different licences.

What the table says for a Python caching decision:

- **`redis-py` is still the answer** for the distributed tier. It is the most active of the

- **`valkey-glide` is the only one of the three built for Valkey first.** Rust core with a

- **`valkey-py` is the conservative fork** — same API as redis-py with an `import valkey as
  redis` alias — but one stable release in the last twelve months puts it behind both
  parents. Use it only where a dependency named "redis" is itself the objection.

## Comprehensive Library Analysis

### 1. **redis-py** (Redis Python Client)
**Technical Specifications**:
- **Performance**: 100,000+ ops/sec, `<1`ms latency
- **Memory**: Efficient binary protocols, optional compression
- **Features**: Pub/sub, transactions, clustering, persistence
- **Ecosystem**: Extensive tooling, monitoring, cloud services

**Strengths**:
- Industry-proven scalability (Instagram, GitHub, Twitter)
- Rich data structures (strings, hashes, lists, sets, sorted sets)
- Built-in persistence and high availability
- Extensive monitoring and operational tools
- Active development and enterprise support

**Weaknesses**:
- Higher memory overhead than pure cache solutions
- Network latency for distributed setups
- Complexity for simple use cases
- Additional infrastructure dependency

**Best Use Cases**:
- Multi-server applications requiring shared state
- Real-time features (leaderboards, counters, sessions)

## Architecture Patterns and Anti-Patterns

### Recommended Patterns:

#### **Multi-Tier Caching**:
```python
# L1: In-memory for hot data
@cachetools.cached(cachetools.TTLCache(maxsize=100, ttl=60))
def hot_data(key):
    # L2: Redis for shared data
    result = redis_client.get(f"shared:{key}")
    if result:
        return json.loads(result)

    # L3: Database for persistent data
    result = database.query(key)
    redis_client.setex(f"shared:{key}", 300, json.dumps(result))
    return result
```

#### **Cache-Aside Pattern**:
```python
def get_user_profile(user_id):
    # Check cache first
    cached = redis_client.get(f"user:{user_id}")
    if cached:
        return json.loads(cached)

    # Load from database
    profile = database.get_user(user_id)

    # Update cache
    redis_client.setex(f"user:{user_id}", 3600, json.dumps(profile))
    return profile
```

#### **Write-Through Caching**:
```python
def update_user_profile(user_id, data):
    # Update database
    database.update_user(user_id, data)

    # Update cache immediately
    redis_client.setex(f"user:{user_id}", 3600, json.dumps(data))
```

### Anti-Patterns to Avoid:

#### **Cache Stampede** (Multiple requests regenerating same data):
```python
# BAD: No protection against simultaneous cache misses
def expensive_operation(key):
    result = cache.get(key)
    if not result:
        result = very_expensive_computation()  # Multiple threads might run this
        cache.set(key, result, ttl=300)
    return result

# GOOD: Use locking or single-flight pattern
import threading
_locks = {}

def expensive_operation(key):
    result = cache.get(key)
    if not result:
        lock = _locks.setdefault(key, threading.Lock())
        with lock:
            result = cache.get(key)  # Double-check
            if not result:
                result = very_expensive_computation()
                cache.set(key, result, ttl=300)
    return result
```

#### **Cache Invalidation Race Conditions**:
```python
# BAD: Data modification without proper cache invalidation
def update_data(key, new_data):
    database.update(key, new_data)
    # Race condition: cache might be repopulated with old data here
    cache.delete(key)

# GOOD: Atomic operations or versioning
def update_data(key, new_data):
    with database.transaction():
        database.update(key, new_data)
        cache.delete(key)
```

**What actually happened (added 2026-08-20)**: the risk above materialised in March 2024 when
Redis 7.4 left BSD for RSALv2 / SSPLv1, and the exit strategy materialised the same month —
the Linux Foundation's Valkey fork, now on 9.1.1 with AWS, Google and Oracle among its
backers and the default engine on ElastiCache and Memorystore. Redis added AGPLv3 back as
an option with 8.0 (2025-05-01). The practical hedge for a Python team is concrete and
cheap: keep `redis-py`, keep the wire protocol, and decide server by licence. The one
irreversible step is upgrading the *data* past Redis 7.2 — Valkey will not read a 7.4+ RDB
— so the exit must be chosen before that upgrade, not after. See S2 §0.
