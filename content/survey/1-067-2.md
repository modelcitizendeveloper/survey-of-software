# 1.067.2 Real-Time Broadcast & Pub/Sub Servers

Self-hostable real-time fan-out servers compared on delivery, recovery, presence, scaling, transports, auth and license; fan-out latency is indistinguishable across Centrifugo, Socket.IO and bare WebSocket on one host.

> [!NOTE]
> **Evidence: [measured, method not yet published](/survey/method/#the-evidence-ladder).** The numbers here were produced by probes run on a stated machine; the harness is not in the public repository yet, so a reader cannot re-run them.


## At a glance


| Library | Best for | Verdict |
|---|---|---|
| **Centrifugo** | Chat and feeds from any backend language | Apache-2.0; history stream with recovery, presence, Redis multi-node in the open edition; PRO is paid |
| **Socket.IO** | Node.js apps with Socket.IO clients | MIT; recovery only on Redis Streams, MongoDB and in-memory adapters; Redis adapter quiet since 2024 |
| **Mercure** | One-way updates with no client library | AGPL-3.0; Last-Event-ID replay; free hub is single node, multi-node is paid |
| **Phoenix Channels and PubSub** | Elixir backends | MIT; replicated Presence and native clustering; no history |
| **NATS (WebSocket)** | Teams already running NATS | Apache-2.0; JetStream durable replay; browser-facing layers are the app's |
| **Laravel Reverb** | Laravel apps or Pusher clients | MIT; healthy; Laravel-centered |
| **Soketi** | Nothing new; migrate off | AGPL-3.0; stalled (42 open PRs, none merged since October 2023; last release 2024-03) |
| **Redis / Valkey pub/sub** | Cross-node relay | At-most-once, no history; Redis 8 tri-license, Valkey BSD-3-Clause |


**What the research found**

- **Every server in the category defaults to at-most-once delivery; what differs is the repair after a gap: Centrifugo history stream, Socket.IO state recovery on two adapters, Mercure Last-Event-ID, NATS JetStream, and nothing for Phoenix, Reverb and Redis pub/sub.** — Keep the application database as the system of record; use the server for delivery and recent catch-up.
- **On one host, fan-out latency does not separate Centrifugo, Socket.IO and a bare WebSocket broadcaster at 1,000 or 4,000 subscribers; the load generator is most of the number.** — Choose on recovery, presence, scaling and license, not on a latency claim.
- **High availability sits on different sides of the license line: Mercure's multi-node needs a paid license, while Centrifugo (Redis), NATS and Phoenix cluster in open source.** — Check the edition before designing for more than one node.
- **Soketi has stalled (42 open PRs, none merged since October 2023, last release March 2024); Laravel Reverb is the maintained Pusher-protocol server.** — Do not start new work on Soketi.
- **Socket.IO connection state recovery does not work with the Redis pub/sub adapter; it needs the Redis Streams or MongoDB adapter, and the Streams adapter is small and pre-1.0.** — Adapter choice decides what survives a disconnect.


**What the research recommends**

**Default** — Choose by what must survive a disconnect and how many nodes you need, then by language and license; keep the database as the record.

| Persona | Pick |
|---|---|
| chat | Centrifugo for a polyglot backend; Phoenix for Elixir; Socket.IO with the Redis Streams adapter for Node, with an application-level catch-up. |
| live dashboards | Mercure on one node, Centrifugo cache mode for several; NATS where it already carries the metrics. |
| notifications | Store in the app database and nudge online clients; Centrifugo user channels, Mercure private updates or Reverb private channels. |
| collaborative presence | Phoenix Presence on Elixir; Centrifugo or a Pusher-protocol server otherwise, re-querying the roster because join/leave is at-most-once. |

# Real-Time Broadcast and Pub/Sub Servers: Domain Explainer

## The hardware-store version

A WebSocket library, covered in [1.067](../1.067-websocket-libraries/), is a telephone line: it connects one client to one server. A broadcast server is the switchboard. It knows who is on the line, which topics they care about, and how to pass one message to ten thousand listeners at once. Plenty of apps start with the telephone line and discover, around the second server or the first dropped connection, that they need the switchboard.

## The problem

A web request answers one question and ends. Anything that should arrive without being asked for (a new chat message, a price tick, a "your export is ready") needs a connection that stays open, and something on the server that decides which connections receive which message.

Three things make this harder than it looks.

**One server stops being enough.** Connections live in one process's memory. When two or more servers sit behind a load balancer, a message published on server A must also reach the clients connected to server B. That needs a shared channel between servers, called a backplane, and each framework solves it differently.

**Networks drop.** Phones go through tunnels and laptops sleep. A message sent while a client is disconnected is, by default, gone. Some systems keep a short history so a returning client can catch up; most do not, and the application must fetch what it missed.

**Who is here?** Chat, collaborative tools and live counters want a roster of connected users. Connections can vanish without saying goodbye, so a roster needs timeouts and reconciliation.

## Approaches

- **A standalone fan-out service** next to the application. The backend publishes over HTTP; browsers connect to the service. Examples: Centrifugo, Mercure.
- **Realtime built into the app server.** The application process holds the connections and shares messages between nodes through an adapter or its runtime. Examples: Socket.IO, Phoenix Channels.
- **A general message bus with a browser door.** A broker used for service-to-service messaging that also accepts WebSocket clients. Example: NATS.
- **A protocol clone.** A self-hosted server that speaks the API of a hosted service so existing clients keep working. Examples: Soketi and Laravel Reverb, which speak Pusher's protocol.
- **A hosted service.** Ably, Pusher Channels and Supabase Realtime run all of it for a fee per message or connection. They appear in this survey only as the alternative to compare against.

Underneath most of these sits a pub/sub relay such as Redis pub/sub, which carries messages between server nodes.

## How a message travels

A backend event happens: a comment is saved. The backend tells the broadcast server which channel it belongs to, usually with one HTTP call or a function call into the framework. The server looks up which connections are subscribed to that channel and writes the message to each. If other server nodes hold more subscribers, it passes the message to them first through the backplane, and each node writes to its own connections. The client library on the other end turns the bytes into an event in the page.

Each step has a failure mode a buyer should ask about: the publish call can succeed while a subscriber is offline; the backplane can drop while the nodes keep running; a client can reconnect to a different node than before. The systems in this survey differ in which of these they repair for you.

## Trade-offs across the whole category

- **Simplicity against capability.** One-way SSE from a hub is the least to learn and run; two-way channels with history, presence and permissions need a real server and a client library.
- **Embedded against separate.** Realtime inside the application reuses its authentication and data model but ties connection count to the app's deploy cycle. A separate service scales and restarts on its own, at the price of another moving part and a second auth path.
- **Open against paid.** Several of these have a free edition with a ceiling (a single node, fewer operations tools) and a paid one without. The ceiling is worth finding before design, not after.
- **Own against hosted.** A hosted service removes operations and bills by messages or connections. A self-hosted one bills by machines and attention.

## Vocabulary

- **Channel, topic, room:** the named group a message is addressed to. Different systems use different words.
- **At-most-once:** a message is delivered once or not at all. **At-least-once:** it is retried until acknowledged, so duplicates are possible.
- **History and recovery:** the server keeps recent messages and replays what a reconnecting client missed.
- **Presence:** the list of who is connected to a channel.
- **Transport:** the connection type. WebSocket is two-way and universal; Server-Sent Events (SSE) is one-way over plain HTTP with built-in reconnection; WebTransport is a newer two-way option over HTTP/3.

## When you need one

- Several app servers share connections.
- You want history, recovery or presence without writing them yourself.
- Updates must reach thousands of clients quickly.

## When you do not

- A single server with a few dozen connections is well served by a plain WebSocket library.
- If updates are rare and a few seconds late is fine, polling is simpler.
- If the only goal is a phone notification when the app is closed, that is mobile push (see [1.119.2](../1.119.2-push-notification-libraries/)), a different layer.

## Sources

The delivery vocabulary follows the documentation of Redis pub/sub (https://redis.io/docs/latest/develop/pubsub/), Socket.IO (https://socket.io/docs/v4/delivery-guarantees) and NATS JetStream (https://docs.nats.io/nats-concepts/jetstream). The backplane idea is described in the Socket.IO adapter documentation (https://socket.io/docs/v4/adapter/). The SSE and EventSource reconnection behavior is defined in the Mercure specification (https://mercure.rocks/spec). Server-Sent Events and WebTransport status were read from the sources cited in S4.

# S1: The field at a glance

Servers and frameworks that take a message from a backend (or another client) and fan it out to many connected browser and app clients. Client-library choice for a single WebSocket connection is covered in [1.067 WebSocket Libraries](../../../1.067-websocket-libraries/); this survey starts one layer up, where the question is channels, rooms, history, presence and more than one server.

## Four shapes

| Shape | Members | What you operate |
|---|---|---|
| Standalone broadcast server | Centrifugo, Mercure | One service next to your app; your backend publishes over HTTP |
| Realtime library inside the app server | Socket.IO, Phoenix Channels | The app process holds the connections |
| General message bus with a WebSocket door | NATS | A broker you may already run; browsers connect through its WebSocket listener |
| Pusher-protocol servers | Soketi, Laravel Reverb | A drop-in for the hosted Pusher API, so existing Pusher clients keep working |

Redis pub/sub is not a client-facing server. It is the backplane several of the above use to share messages between nodes, and it is profiled that way.

Ably, Pusher Channels and Supabase Realtime are hosted services. They appear as neighbors in hosted-neighbors.md so a reader can see what self-hosting trades away; they are not scored.

## Evaluation dimensions

1. **Delivery guarantee.** At-most-once, at-least-once, ordered or not.
2. **History and recovery.** What a client gets back after a dropped connection.
3. **Presence.** Who is connected to a channel right now.
4. **Horizontal scaling.** What it takes to run two or more nodes, and which edition allows it.
5. **Transports.** WebSocket, SSE, HTTP streaming, WebTransport.
6. **Authentication and authorization.** How a client proves identity and which channels it may join.
7. **License and viability.** What the license obliges, and whether the project is still maintained.

## Boundary

In scope: self-hostable servers that fan out to browsers and mobile apps. Out of scope: document-state synchronization (CRDT libraries such as Yjs handle merging edits, and run on top of one of these transports), mobile push through APNs or FCM (see [1.119.2 Push Notification Libraries](../../../1.119.2-push-notification-libraries/)), task queues (see 1.043.1), and WebRTC media.

# Centrifugo

A standalone real-time messaging server written in Go. Your backend, in any language, publishes to it over an HTTP or gRPC API; clients subscribe to channels through official SDKs for JavaScript, Swift, Java, Dart, C# and Go (source: https://centrifugal.dev/docs/getting-started/introduction, accessed 2026-10-05). The same code base is available as a Go library, `centrifuge` (MIT).

## Facts

| | |
|---|---|
| License | Apache-2.0 server; a paid PRO edition adds features (source: https://api.github.com/repos/centrifugal/centrifugo, accessed 2026-10-05) |
| Latest release | v6.9.7, 2026-09-29 (source: GitHub releases API, accessed 2026-10-05) |
| Stars | about 10.8k (source: GitHub API, accessed 2026-10-05) |
| Stall test | 6 open PRs, 117 merged since 2026-04-05 (source: GitHub search API, accessed 2026-10-05) |
| Transports | WebSocket, HTTP streaming, SSE, gRPC, WebTransport (experimental) (source: https://centrifugal.dev/docs/transports/overview) |
| Delivery | At-most-once pub/sub; recovery replays missed messages from a bounded history stream |
| History | Per-channel stream with `history_size` and `history_ttl`; epoch and offset let a reconnecting client check it has the same stream |
| Presence | Presence query, presence stats, join/leave events; join/leave are at-most-once |
| Scaling | Memory engine for one node; Redis (or Redis-compatible) engine for many nodes with history and presence; NATS broker for many nodes without history; PostgreSQL broker marked experimental |
| Auth | Connection JWT (HMAC, RSA, ECDSA; EdDSA via JWKS), a backend connect proxy, subscription tokens, per-namespace permission flags |

## Behavior to know

- Channels default to deny. A subscription from a client is refused until the channel's namespace sets `allow_subscribe_for_client`, and an anonymous user also needs `allow_subscribe_for_anonymous` (measured 2026-10-05; Centrifugo 6.9.7; a subscribe without it returned code 103 permission denied).
- Recovery has two modes: stream mode replays every missed publication, cache mode delivers only the latest one. Cache mode suits dashboards and tickers (source: https://centrifugal.dev/docs/server/history_and_recovery).
- A `recovered: false` result tells the app to reload state from its own database. The docs call streams ephemeral.

## Edition line

PRO is a paid license, quoted on request, and adds push notification API, rate limiting, user blocking and token revocation APIs, tracing, SSO for the admin UI, and delta compression among others (source: https://centrifugal.dev/docs/pro/overview). The open-source edition already includes multi-node Redis scaling, history, presence and recovery.

## Trade-offs

- Strong on the features chat and feeds need, with the history model written down plainly.
- A separate process to deploy and a client SDK to adopt; the SDK is required for the bidirectional transports.
- History is a sliding window, not storage of record.

## What self-hosting trades away

- **Operations.** Connection capacity planning, TLS termination, a proxy that does not break WebSockets or SSE, and a backplane to run.
- **Metering shape.** Hosted prices scale with messages or connections; self-hosted cost scales with machines. Flat daily caps (Pusher) and per-message metering (Ably) behave differently under a burst.
- **Protocol lock-in.** The Pusher protocol is implemented by the Soketi and Reverb servers, so leaving Pusher Channels is cheap. Ably's and Supabase's client protocols are theirs; Centrifugo and Mercure are alternatives with different protocols.
- **Features.** Ably documents history and delivery features as a product; in the self-hosted set only Centrifugo (history and recovery) and NATS JetStream cover the same ground.

# Mercure

An open protocol and a reference hub for pushing updates to browsers over Server-Sent Events. A backend publishes with a plain HTTP POST; browsers subscribe with the native EventSource API, no client library required. The hub is a Go module that runs inside Caddy.

## Facts

| | |
|---|---|
| License | AGPL-3.0 for the hub (source: https://api.github.com/repos/dunglas/mercure, accessed 2026-10-05); paid Self-Hosted and Cloud editions |
| Latest release | v1.0.3, 2026-10-03 (source: GitHub releases API, accessed 2026-10-05) |
| Stars | about 5.3k (source: GitHub API, accessed 2026-10-05) |
| Stall test | 10 open PRs, 187 merged since 2026-04-05 (source: GitHub search API, accessed 2026-10-05) |
| Transport | SSE over HTTP; HTTP/2 or later recommended for multiplexing (source: https://mercure.rocks/spec) |
| Delivery | Best effort; the spec says a subscriber should not assume no events are lost |
| Recovery | Event ids and the `Last-Event-ID` header or `lastEventID` query parameter replay events after a disconnect |
| Presence | Optional subscriptions API lists active subscriptions and publishes subscription events |
| Scaling | The open-source hub is single-node with a BoltDB transport; multi-node needs the Self-Hosted license, with Redis/Valkey, PostgreSQL, Kafka or Pulsar transports (source: https://mercure.rocks/docs/hub/cluster) |
| Auth | JWT for publishers and subscribers, private updates, topic selectors |

## Behavior to know

- Version 1.0 changed authentication. The hub's default configuration validates access tokens in a stricter mode (issuer, audience and scope claims, RFC 9068 style), and the legacy simple-JWT setup runs only under an explicit compatibility switch (measured 2026-10-05, v1.0.3: a token carrying only the classic `mercure` claim was rejected with 401 on the default configuration; the subscribe parameter `topic` was refused with a message pointing to `match`). Tutorials written for 0.x do not work unchanged.
- The cluster page states that open source, Cloud and Self-Hosted tiers speak the same protocol, so a client can move between them by changing the hub URL. Self-Hosted tiers are listed from 1,500 to 12,000 euros or more a year (source: https://mercure.rocks/docs/hub/cluster, accessed 2026-10-05).
- AGPL-3.0 obliges anyone who modifies the hub and offers it over a network to publish those modifications; running it unmodified behind an app creates no such duty for the app.

## Trade-offs

- Smallest client footprint: browsers, mobile webviews and any HTTP client work with no SDK.
- One-way only: clients receive; sending goes through your own HTTP endpoints.
- High availability is the paid line; free users run one node.

# NATS with WebSocket

A messaging system written in Go. Core NATS is subject-based publish/subscribe with request-reply; JetStream adds persistence. The server has a built-in WebSocket listener, so browsers connect straight to the broker with the JavaScript client.

## Facts

| | |
|---|---|
| License | Apache-2.0 (source: https://api.github.com/repos/nats-io/nats-server, accessed 2026-10-05) |
| Latest release | v2.15.0, 2026-09-17 (source: GitHub releases API, accessed 2026-10-05) |
| Stars | about 20.8k (source: GitHub API, accessed 2026-10-05) |
| Stall test | 22 open PRs, 415 merged since 2026-04-05 (source: GitHub search API, accessed 2026-10-05) |
| Browser client | `nats.ws`, about 71k downloads a week (source: https://api.npmjs.org/downloads/point/last-week/nats.ws, week ending 2026-10-03); the current client packages are `@nats-io/nats-core` and `@nats-io/transport-node` |
| Transports | NATS protocol over TCP; WebSocket listener with optional TLS, compression, origin allow-list, JWT cookie (source: https://docs.nats.io/running-a-nats-service/configuration/websocket/websocket_conf) |
| Delivery | Core NATS is at-most-once to currently connected subscribers; JetStream gives at-least-once with acknowledgements and redelivery (source: https://docs.nats.io/nats-concepts/jetstream) |
| History and recovery | JetStream streams replay from a start, a sequence or a time; consumers track position |
| Presence | None built in; subscription and connection events can be observed with system accounts |

## Behavior to know

- A browser that connects to NATS speaks the broker's own protocol with its subject model; there is no channel-permission layer designed for end users in the way Centrifugo or Pusher-style servers have one. Per-user subject permissions and auth callout are the tools for restricting what a browser can subscribe to.
- NATS is a good fit when the broker already carries internal traffic and the same subjects should also reach browsers. It is a heavier commitment than a fan-out gateway when nothing else uses it.
- Centrifugo can use NATS as its inter-node broker, without history or presence.

## Trade-offs

- Highest project velocity in the set and open-source clustering and persistence.
- Browser-facing concerns (presence, per-channel recovery for UI clients, user-scoped channels) are yours to assemble.

# Phoenix Channels and PubSub

The realtime layer of the Elixir web framework Phoenix. Channels give topic-based message routing over WebSocket (with long-polling as the only other transport); `Phoenix.PubSub` distributes broadcasts across nodes; `Phoenix.Presence` tracks who is on a topic.

## Facts

| | |
|---|---|
| License | MIT (source: https://api.github.com/repos/phoenixframework/phoenix, accessed 2026-10-05) |
| Latest release | v1.8.15, 2026-09-25 (source: GitHub releases API, accessed 2026-10-05) |
| Stars | about 23k (source: GitHub API, accessed 2026-10-05) |
| Stall test | Phoenix: 32 open PRs, 126 merged since 2026-04-05; phoenix_pubsub: 6 open, 3 merged (source: GitHub search API, accessed 2026-10-05) |
| Transports | WebSocket and long-polling (source: https://phoenix.hexdocs.pm/channels.html) |
| Delivery | At-most-once; the server persists nothing, so a restart loses undelivered messages and offline clients miss what was sent |
| History and recovery | None built in; the application stores and replays |
| Presence | `Phoenix.Presence`: replicated across the cluster with no single source of truth and no external dependency (source: https://phoenix.hexdocs.pm/presence.html) |
| Scaling | Erlang distribution between nodes, one message sent per additional node; a Redis adapter exists for environments without distributed Elixir (source: channels guide) |
| Auth | Per-socket connect callback and per-channel join callback, both in app code |

## Behavior to know

- The server and the app are the same program. Channels reuse the app's authentication and database, which removes a network hop and a service boundary, and requires the backend to be Elixir.
- Clients are the Phoenix JavaScript library, plus community clients for Swift, Kotlin and others. The wire format is Phoenix's own, so there is no generic client.
- Connections are Erlang processes. Fan-out cost per node comes from the BEAM scheduler; no benchmark for it is included here because this survey's harness did not stand up an Elixir app.

## Trade-offs

- The most complete built-in presence story in the field, and clustering with no extra infrastructure.
- Not usable by a team that does not run Elixir; the Redis adapter is a niche escape hatch.
- No history means recovery is entirely your design.

# Pusher-protocol servers: Soketi and Laravel Reverb

The Pusher Channels protocol has two halves: a WebSocket client protocol with public, private and presence channels, and a signed HTTP API for publishing. Servers that implement it let an app switch from hosted Pusher to self-hosting by changing a host name. Presence channels and private-channel authorization are part of the protocol.

## Laravel Reverb

A first-party Laravel WebSocket server in PHP on a ReactPHP event loop, speaking the Pusher protocol so Laravel Echo and Pusher clients work (source: https://laravel.com/docs/12.x/reverb).

# S1 recommendation: which shape fits which situation

| If you have | Look first at | Why |
|---|---|---|
| A backend in any language and a need for history, recovery and presence at moderate scale | Centrifugo | Only standalone server here with replay from a bounded stream and Redis-backed multi-node in the open-source edition |
| An Elixir backend | Phoenix Channels and Presence | Clustering and presence need no extra service; recovery is yours to build |
| A Node.js backend and a Socket.IO-shaped client | Socket.IO with the Redis Streams adapter if you want recovery | Biggest community; the adapter choice decides what survives a disconnect |
| One-way updates to browsers and a wish for no client SDK | Mercure (single node) | Native EventSource, plain HTTP publish; high availability is a paid license |
| NATS already in production | NATS WebSocket listener | Reuses the broker; the browser-facing layers are yours |
| A Laravel app, or Pusher clients already in place | Laravel Reverb | Same protocol as hosted Pusher; avoid Soketi because it has stalled |
| Several app nodes behind a load balancer and nothing else | Redis (or Valkey) as the backplane | Cheapest cross-node relay; it is at-most-once and stores nothing |

## Findings that cut across the field

1. **Almost every server here is at-most-once.** Centrifugo, Socket.IO, Phoenix, Mercure, Reverb and Redis pub/sub all say so in their docs. Replay after a gap is the feature that varies: Centrifugo (history stream), Socket.IO (state recovery on two adapters), Mercure (Last-Event-ID, best effort) and NATS JetStream have it; Phoenix and Pusher-protocol servers do not.
2. **High availability sits on different sides of the license line.** Centrifugo's Redis-backed multi-node is in the Apache-2.0 edition, Phoenix clusters natively, NATS clusters in open source, and Mercure's multi-node requires a paid Self-Hosted license.
3. **The server's protocol decides the client.** Socket.IO, Phoenix, Centrifugo and NATS each need their own client library; Mercure needs none; Pusher-protocol servers reuse Pusher's clients.
4. **One project has stalled.** Soketi shows 42 open PRs and none merged since October 2023, with no release since March 2024.
5. **Licenses differ in what they ask.** Apache-2.0 and MIT for Centrifugo, NATS, Socket.IO and Phoenix; AGPL-3.0 for Mercure and Soketi.

# Redis pub/sub as a backplane

Redis pub/sub is a channel-based message relay inside Redis. It is not a client-facing server: browsers do not talk to it. Socket.IO, Centrifugo, Laravel Reverb and Phoenix's Redis adapter use it so that a message published to one app node reaches subscribers connected to the others.

## Semantics

- **At-most-once.** A message is delivered once if at all; a subscriber that is disconnected or too slow loses it permanently (source: https://redis.io/docs/latest/develop/pubsub/, accessed 2026-10-05).
- **Ordered per publisher.** Subscribers receive messages in publish order.
- **Fire-and-forget.** Nothing is stored. Redis Streams add persistence and at-least-once delivery, and are what the Socket.IO Streams adapter and Centrifugo's history use.
- **Sharded pub/sub (Redis 7.0 and later).** Shard channels hash to cluster slots and propagate only within a shard, which limits cluster-bus traffic and lets pub/sub scale by adding shards (source: same page).

## Licensing

The license of the server underneath matters when it is a component of your deployment.

| Redis 7.4 to 7.8 | RSALv2 or SSPLv1 |
| Redis 8.0 and later | RSALv2, SSPLv1 or AGPLv3, your choice |
| Valkey (Linux Foundation fork) | BSD-3-Clause (source: GitHub API, accessed 2026-10-05) |

(source: https://redis.io/legal/licenses/, accessed 2026-10-05). Centrifugo documents compatibility with Valkey, KeyDB, DragonflyDB and managed Redis services (source: https://centrifugal.dev/docs/server/engines). Valkey 9.1.2 was released 2026-09-01 and Redis 8.10.2 on 2026-09-17 (source: GitHub releases API).

## Failure behavior

If the connection to Redis drops, Socket.IO's adapter keeps delivering only to clients on the local node (source: https://socket.io/docs/v4/redis-adapter/). Messages published during the gap do not reach other nodes later. A backplane outage therefore shows up as partial delivery rather than an error.

## When the backplane is the wrong tool

Redis pub/sub has no history, so it cannot support recovery by itself, and every node receives every message on the channels it subscribes to. NATS, Kafka and managed pub/sub services are alternatives with their own durability. The Socket.IO adapters list covers Postgres, MongoDB and three cloud buses for teams that do not run Redis.

## Behavior to know

- Sticky sessions are required when long-polling is enabled across multiple nodes; without them clients get HTTP 400 from a node that does not know the session (source: https://socket.io/docs/v4/redis-adapter/).
- The Redis adapter carries no data persistence and no authentication; anyone who can publish to its channels can inject packets, so Redis must stay on a trusted network.
- If Redis drops, broadcasts reach only clients on the node that sent them.
- The Redis pub/sub adapter and connection state recovery are mutually exclusive; recovery needs the Redis Streams adapter, which has a much smaller footprint (42 stars; 0.3.1, 2026-03-12; source: GitHub API).
- The Redis adapter: last release 8.3.0 on 2024-03-13, 10 open PRs and none merged since 2026-04-05 (source: GitHub). It is stable and quiet rather than abandoned, but it is the part of the stack with the least movement.

## Trade-offs

- Largest community and client matrix of the group; the protocol is custom, so only Socket.IO clients talk to a Socket.IO server.
- The library lives inside the app process, so deploys and connection counts are coupled to the app.
- Server-to-client recovery depends on picking the right adapter.

# Configuration shapes

Two short examples where the setting is the difference between servers. Both ran in the benchmark harness (measured 2026-10-05, Centrifugo 6.9.7, Mercure v1.0.3).

## Centrifugo: channels are closed until opened

```json
{
  "client": { "allow_anonymous_connect_without_token": true },
  "channel": { "without_namespace": {
      "allow_subscribe_for_client": true,
      "allow_subscribe_for_anonymous": true } },
  "http_api": { "key": "<api key>" }
}
```

Without the two `allow_subscribe_*` flags, a client that connected successfully was refused on subscribe with code 103 (permission denied). Production setups use connection JWTs and subscription tokens instead of anonymous access.

## Mercure 1.0: legacy tokens need an explicit switch

```
mercure {
    publisher_jwt  {env.MERCURE_KEY} HS256
    subscriber_jwt {env.MERCURE_KEY} HS256
    anonymous
    protocol_version_compatibility 8
}
```

The default 1.0 configuration validates access tokens in a stricter mode with issuer, audience and scope claims. # Delivery guarantees and recovery

## What at-most-once means to a user

A message is sent once. If the client's connection is down at that moment, or its buffer is full, or the node restarts, the message is gone. All of the servers in this survey default to this. They differ in what they offer to repair a gap after the fact.

## Four recovery designs

**1. Bounded history stream with a position (Centrifugo).** Every channel with history enabled keeps a sliding window of recent publications, each with an incrementing offset, under a stream identifier called an epoch. A reconnecting client sends its last epoch and offset. If the epoch matches and all missed offsets are still in the window, the server replays them and reports `recovered: true`; otherwise it reports `recovered: false` and the application must reload state from its own store (source: https://centrifugal.dev/docs/server/history_and_recovery). Window size and TTL are per-namespace settings, and the docs describe streams as ephemeral. An optional positioning check disconnects a client whose stream has a gap (disconnect code 3010) so it recovers on reconnect. The same page describes a cache mode that delivers only the latest publication, for dashboards and tickers.

**2. Session and packet backup (Socket.IO).** The server hands the client a session id and an offset on every packet. Within `maxDisconnectionDuration`, a reconnecting client regains its socket id, rooms and the packets it missed. It works with the in-memory, Redis Streams and MongoDB adapters, not the Redis pub/sub adapter, and the docs say recovery will not always succeed (source: https://socket.io/docs/v4/connection-state-recovery). Server-to-client at-least-once beyond that is application logic with event ids and stored offsets (source: https://socket.io/docs/v4/delivery-guarantees).

**3. Event id replay (Mercure).** Each update carries an id; the browser's EventSource sends the last one in `Last-Event-ID` on reconnect, and the hub sends everything after it. The spec says hubs may discard older events by policy and subscribers should not assume nothing was lost (source: https://mercure.rocks/spec). This is built into the EventSource API, so the browser does the bookkeeping.

**4. Durable stream with acknowledgements (NATS JetStream).** Streams persist messages and consumers track a position; unacknowledged messages are redelivered, giving at-least-once. Replay can start from the beginning, a sequence number or a time (source: https://docs.nats.io/nats-concepts/jetstream). A browser can use it through the WebSocket listener, at the price of handling consumers and acknowledgements in client code.

## What has no recovery

Phoenix Channels, Reverb and other Pusher-protocol servers, and Redis pub/sub have no replay. The Phoenix guide says applications needing stronger guarantees must add persistence and recovery themselves (source: https://phoenix.hexdocs.pm/channels.html). The usual pattern for all of these is to store messages in a database and have a reconnecting client fetch what it missed by id or timestamp, which is also the fallback when any of the four recovery designs above reports failure.

## Presence delivery

Presence is a view of who is connected, and it carries the same at-most-once nature. Centrifugo states that join and leave events are delivered at most once (source: https://centrifugal.dev/docs/server/presence), so a client should treat the presence query as the truth and the events as hints. Phoenix Presence replicates state between nodes without a central source and self-heals (source: https://phoenix.hexdocs.pm/presence.html).

# Fan-out latency on one host

## Workload

N subscribers connect to one server on the same machine, using each server's official client library in Node.js. A backend publisher sends one JSON message of about 100 bytes every 100 ms (10 messages a second) through the server's publish API: HTTP POST for Centrifugo, Mercure, the Socket.IO control server and the bare `ws` control; the native TCP client for NATS. Subscribers receive over WebSocket (Centrifugo, Socket.IO, NATS and `ws`) or SSE (Mercure). Each message carries a monotonic-clock timestamp taken just before the publish call; each subscriber records the difference when its callback fires. Ten warmup messages are excluded. Latency is therefore publish call to client callback, one way, and includes the HTTP publish for four of the five targets.

Subscribers run in four worker threads that share the same monotonic clock. 1,000 subscribers: 100 measured messages per run, three runs per target, alternating target order. 4,000 subscribers: 60 messages per run, two runs. Recipes and raw output are in `harness/1-067-2-realtime-broadcast-pubsub/` (`run-all.sh`, `results/n1000.jsonl`, `results/n4000.jsonl`).

## Environment

(measured 2026-10-05) Linux 6.6.87.2-microsoft-standard-WSL2, aarch64, 8 logical CPUs, 11 GB RAM, with other containers running on the host; Node.js v20.20.0; Centrifugo v6.9.7 (memory engine, defaults except permission flags); Socket.IO 4.8.4 server and client with WebSocket transport only and the default in-memory adapter; Mercure hub v1.0.3 in protocol-compatibility mode 8 with BoltDB defaults; NATS server v2.15.0 with a no-TLS WebSocket listener and `@nats-io/nats-core` 3.4; `ws` 8.22 as a floor. One machine runs servers, publisher and all subscribers, so they compete for CPU.

## Results

1,000 subscribers, median across 3 runs (measured 2026-10-05; milliseconds):

| Target | p50 | p90 | p99 | max | Delivered |
|---|---|---|---|---|---|
| bare `ws` broadcast (floor) | 14.9 | 27.9 | 37.8 | 42.2 | 100% |
| Centrifugo | 15.7 | 27.6 | 38.2 | 62.2 | 100% |
| Socket.IO | 14.4 | 30.5 | 56.3 | 77.3 | 100% |
| NATS (WebSocket) | 19.0 | 38.8 | 56.7 | 68.7 | 100% |
| Mercure (SSE) | 33.8 | 56.1 | 88.2 | 117.4 | 100% |

4,000 subscribers, median across 2 runs (measured 2026-10-05; milliseconds):

| Target | p50 | p90 | p99 | max | Delivered |
|---|---|---|---|---|---|
| bare `ws` broadcast (floor) | 39.2 | 77.8 | 93.9 | 104.6 | 100% |
| Socket.IO | 41.3 | 75.9 | 93.9 | 110.1 | 100% |
| Centrifugo | 47.9 | 80.7 | 93.5 | 112.3 | 99.98% (one run lost 49 of 240,000) |
| NATS (WebSocket) | 50.6 | 86.3 | 114.7 | 137.9 | 100% |
| Mercure (SSE) | 65.6 | 95.6 | 127.9 | 150.4 | 100% |

## How to read it

- **The load generator is most of the number.** The bare `ws` floor is 15 ms at p50 with 1,000 subscribers and 39 ms with 4,000, with no framework in the path. Each worker thread processes its subscribers' callbacks one after another, so latency grows with subscribers per thread. Differences smaller than the floor's own run-to-run spread are not evidence of a faster server.
- **Run-to-run spread is wide.** At 1,000 subscribers the p50 of Centrifugo ranged from 14.5 to 28.5 ms across its three runs, and p99 of Socket.IO from 50 to 65 ms. A first set of runs with every subscriber on a single loopback address gave the same ordering (appendix file `n1000_single-ip.jsonl`) with some p99 outliers up to 494 ms, which is why subscribers were later spread over four loopback addresses; the host's ephemeral port range here is only 4,096 ports, which blocked a single-address run at 5,000.
- **What the data supports.** Centrifugo, Socket.IO and the bare `ws` floor are indistinguishable at 1,000 subscribers; NATS sits a few milliseconds above; Mercure is about twice as high at 1,000 subscribers (p50 33.8 against 14.4 to 15.7 ms) and about 1.5x at 4,000 (65.6 against 41 to 48 ms). Mercure's number includes the cost of the SSE client library in Node and Caddy's HTTP layer, so it describes this stack, not the Mercure protocol.
- **Delivery was complete in nine of ten runs at 4,000 subscribers.** One Centrifugo run delivered 99.98% of messages. The cause was not isolated: the survey did not capture client or server logs for it. Because all servers default to at-most-once, a skipped message under load is within their contract.

## What this does not measure

Multi-node fan-out through a backplane, history or recovery cost, TLS, a real network, publishers that are browsers, message sizes other than about 100 bytes, rates above 10 messages a second, or Phoenix and Reverb (they need an application to host them). Memory use per connection was not recorded. The Mercure run used its legacy-compatibility configuration, because the default 1.0 token rules could not be satisfied from the documentation within the time available.

Documented limits are mostly about the operating system, not the server:

# Persona: chat

## Situation

Rooms or direct conversations, messages that must not silently vanish, users who switch networks and wake laptops, and a need to show who is online or typing.

## What matters

- **History and recovery.** After a reconnect the client must catch up or know it cannot. Every server here is at-most-once, so the question is the repair path.
- **Per-room authorization.** A user may join some rooms and not others.
- **Two-way traffic.** Sending a message and typing indicators.
- **Presence at room scale.**

## Options

- **Centrifugo.** A history stream per room, with offset and epoch recovery, a `recovered` signal that says when to reload from the database, presence and join/leave, and per-namespace permissions. Backend can be any language. The open-source edition scales across nodes with Redis.
- **Phoenix Channels.** Excellent presence and clustering when the backend is Elixir. Recovery is built by the application: store messages, fetch by id after reconnect.
- **Socket.IO.** Rooms are first-class and the community is large. For recovery, run the Redis Streams or MongoDB adapter rather than the Redis pub/sub adapter, and keep an application-level fetch for the cases recovery cannot cover. Presence is application code.
- **NATS JetStream.** Strong durability when the team already runs it; per-room permissions and presence are yours.
- **Mercure.** One-way, so sending goes through your HTTP API and receiving through SSE. Workable for small chat; presence through the subscriptions API; multi-node needs the paid license.

## Verdict

Centrifugo for a polyglot backend; Phoenix when the stack is Elixir; Socket.IO when the stack is Node and the team accepts storing history in its own database. Whichever is chosen, keep messages in a database and treat server-side history as a cache of recent ones.

# Persona: collaborative presence

## Situation

A shared document, board or form where people want to see who else is here, where their cursors are and what they are selecting. Updates are small, frequent and disposable: a stale cursor position is useless a second later.

## What matters

- **A reliable "who is here" list.** Joins, leaves and crashed tabs must resolve to a correct roster.
- **Cheap ephemeral broadcasts** for cursor and selection data, with no need for history.
- **Cluster-consistent presence** if more than one node serves a room.

## Options

- **Phoenix Presence.** Built to replicate a roster across nodes without a central store and to self-heal; changes broadcast on PubSub. The strongest built-in answer for an Elixir team.
- **Centrifugo.** Presence query, presence stats and join/leave events, with per-connection info attached from the token. Join and leave are at-most-once, so clients should poll or re-query the roster occasionally. Presence uses extra server state, so enable it only on namespaces that need it (source: https://centrifugal.dev/docs/server/presence).
- **Pusher-protocol servers (Reverb).** Presence channels are part of the protocol and expose a member list to clients.
- **Socket.IO.** No presence service. Apps keep a roster in the server or Redis and update it from connect and disconnect events; listing sockets in a room works across nodes through the adapter.
- **Mercure.** Subscriptions API publishes subscription events, which can drive a roster but gives no client-to-client path.
- **Hosted Supabase Realtime.** Offers Broadcast and Presence as a service (vendor: https://supabase.com/docs/guides/realtime); its server is open source (Apache-2.0).

## Verdict

Phoenix Presence if on Elixir; Centrifugo or a Pusher-protocol server otherwise, accepting at-most-once join and leave events and re-querying the roster; Socket.IO when the team already builds on it and is willing to own the roster. Merging concurrent edits to document content is a separate library layered on the same transport.

# Persona: live dashboards

## Situation

Metrics, prices, queue depths or job progress shown to many viewers. Updates are server to client only, a missed tick is replaced by the next one, and the newest value is what matters on reconnect.

## What matters

- **Latest-value recovery.** A viewer returning from a sleeping laptop should see the current state, not replay of every tick.
- **Cheap fan-out to many viewers** of the same channel.
- **Proxy-friendliness.** One-way traffic can ride plain HTTP.

## Options

- **Mercure.** SSE with the browser's own EventSource, no client library, and `Last-Event-ID` resume. Publishing is a plain HTTP POST from the metrics job. Single node on the open-source hub; multiple nodes need a Self-Hosted license. AGPL-3.0 applies to the hub.
- **Centrifugo.** Cache recovery mode delivers only the most recent publication on reconnect, which matches the need exactly. It also offers unidirectional SSE and WebSocket transports that work with native browser APIs.
- **NATS.** Subjects per metric and JetStream key-value for the current value; the browser needs the NATS client and permission setup. A fit if NATS already carries the metrics.
- **Socket.IO.** Works, with rooms per dashboard; replay is not needed here, so the adapter choice matters only for multi-node scaling.
- **Redis pub/sub as the only layer.** Not reachable from browsers.

## Verdict

Mercure for a single-node, minimal-client setup; Centrifugo when more than one node is needed without a license fee, or when the latest-value recovery is required; NATS when it is already the metrics bus. The fan-out numbers in the benchmark page show all four deliver within tens of milliseconds at 1,000 subscribers on one host, which is far below dashboard refresh needs.

# Persona: notifications

## Situation

In-app alerts to individual users: a comment reply, a finished export, a payment result. Each message is for one user (or a small group), must not leak to anyone else, and matters even if the user is offline when it fires.

## What matters

- **Per-user channels with enforced privacy.**
- **A fallback for offline users.** Real-time servers deliver to connected clients; a user who is away needs the notification stored and shown on return, or sent through email or mobile push.
- **Many mostly idle connections**, with low traffic per connection.

## Options

- **Centrifugo.** User-limited channels (the `#` boundary reserves a channel to a named user) and connection JWTs make per-user delivery a configuration matter (source: https://centrifugal.dev/docs/server/channels). A push notification API for device tokens exists in the paid PRO edition.
- **Mercure.** Private updates are matched against the subscriber's token, so a per-user topic stays private; SSE reconnects with `Last-Event-ID` replay recent ones.
- **Laravel Reverb or any Pusher-protocol server.** Private channels with a signed auth endpoint, a natural fit if the app is on Laravel or already uses Pusher clients. No replay.
- **Phoenix Channels.** A per-user topic joined after authentication; recovery is the app's job.
- **Socket.IO.** One room per user id, joined in handshake middleware.
- **Hosted Pusher or Ably.** Per-connection pricing makes a large number of idle connections the cost driver; compare against machine cost.

## Verdict

The deciding step is storing notifications in the application database and using the real-time server only to nudge connected clients. With that in place, any server here works; choose by the language and protocol the team already runs. Mobile and offline delivery is outside these servers and covered in [1.119.2](../../../1.119.2-push-notification-libraries/).

## What AGPL changes in practice

AGPL-3.0 applies to the program covered by it. A hub run unmodified beside an application, and reached only over the network, does not extend the license to the application. A team that patches the hub and exposes the patched version to users owes those users the patch source. Legal review of a specific deployment is outside this survey.

## Editions that change what you can do

Mercure's free hub is limited to one node; the license is the high-availability switch. Centrifugo's open-source edition scales across nodes with Redis, so its paid PRO line sits at operations and push features. A requirement list that includes multi-node, push notifications and rate limiting reads very differently across the two.

# Portability and exit

How hard it is to leave each option, in terms of the things the application is coupled to.

| Option | Client coupling | Server-side coupling | Exit path |
|---|---|---|---|
| Centrifugo | Centrifugo SDKs and protocol | HTTP/gRPC publish API; channel and namespace config | Rewrite client subscriptions and publish calls; history is not portable |
| Socket.IO | Socket.IO client and protocol | Rooms, namespaces and events inside app code | Rewrite both sides; the most application-embedded option |
| Mercure | Native EventSource | One HTTP POST per publish, JWT in a header | Smallest exit cost; any SSE-capable hub can replace it, and the three tiers share one protocol |
| Phoenix Channels | Phoenix JS client | Channel modules in Elixir | Tied to Elixir |
| NATS | NATS client | Subjects, JetStream consumers | Moves with the broker; browser code changes |
| Reverb or Soketi | Pusher clients | Pusher HTTP API | Cheapest to move between Pusher-protocol servers and hosted Pusher |
| Redis pub/sub | None for browsers | Pub/sub commands | Replace with Valkey with no code change; other brokers need an adapter |

## Practice

Put publishing behind one function in the backend and keep subscription setup in one client module. That confines a migration to two files. Where recovery matters, keep message storage in the application database so that no server's history format becomes the only copy.

# S4 recommendation

- **Safest long-term bets by activity and license:** NATS (Apache-2.0, 415 merges in six months), Centrifugo (Apache-2.0, 117), Phoenix (MIT, 126).
- **Take care with:** Soketi (stalled; move to Reverb or Centrifugo), the Socket.IO Redis Streams adapter (small and pre-1.0 yet required for recovery), Mercure's AGPL-3.0 and paid multi-node line.
- **Keep the transport behind your own thin publishing function.** Backends publish through an HTTP call in Centrifugo, Mercure, Reverb and Soketi alike; wrapping that call in one module keeps a later switch to a different server contained to that module and the client SDK.
- **Standards help portability.** Mercure is a published protocol with a spec, Pusher's protocol has two independent open implementations, and SSE and WebSocket are browser standards. Socket.IO, Phoenix, Centrifugo and NATS clients are tied to their servers.
- **WebTransport is now in all three major engines** (Safari 26.4, March 2026 per one secondary report and caniuse.com/webtransport; Chrome since 97; Firefox since 114; source: https://webrtc.ventures/2026/04/webtransport-is-now-baseline-what-it-means-for-real-time-media/, accessed 2026-10-05), but Centrifugo still labels its server support experimental and not recommended for production (source: https://centrifugal.dev/docs/transports/webtransport). Plan on WebSocket and SSE.

## Patterns

- **License changes are the main strategic risk in the backplane.** The Redis license moved from BSD to source-available to a tri-license that includes AGPL in the span of 2024 to 2025 (source: https://redis.io/legal/licenses/). A team that wants a permissive license underneath can use Valkey, which Centrifugo lists as compatible.
- **Open-source ceilings.** Mercure's free hub is single-node; Centrifugo's PRO adds operational and push features, not core multi-node. Check which side of the line a requirement sits on before committing.
- **Components age differently from their servers.** Socket.IO is active while the Redis adapter's last release is from March 2024. Adapters are where durability questions land, so their repositories deserve their own check.
