Sortie

Everyone knows to just use sorted(). Here is where that costs you — measured in your browser, not quoted at you.

Sorting is the most settled problem in computing, which is exactly why the received wisdom goes unexamined. sorted() is an excellent default and it is the right answer most of the time. The interesting question is not which library is fastest — it is when the default stops being right, and what the alternative actually gives you.

This page runs the comparisons live. Nothing below is a number I typed in; anything cited from research rather than measured here is labelled as such.

1. The mistake that scales

You are keeping a leaderboard. A score arrives, you add it, you want the list in order. The obvious code re-sorts the list every time a score comes in.

The alternative is to never sort at all: find where the new score belongs and insert it there, keeping the list ordered the whole way through.

Both are correct. One does O(n² log n) work and the other does O(n log n), so the gap does not stay small — it widens with your data, which is why this survives code review and fails in production.

3. The case this tab cannot run

100 million rows. The survey reports sorted() at roughly 30 seconds against about 2 seconds for polars — a ~15× gap. polars is available in this browser runtime, but 100M rows is not: it will not fit in a tab's memory budget.

So this number is cited from Survey of Software 1.001, not measured here. Reproducing it needs native Python and real RAM — which is the honest boundary of a floor model, and the reason the research exists as well as the demo.

What each one actually gives you

Speed is the least interesting axis, and the one every listicle stops at. These libraries are not competing implementations of the same idea — they do different things, and the reason to pick one is usually a capability rather than a benchmark.

sorted()Stable. Sorts anything comparable. key= takes any function. The right default, and the only one that needs no dependency.
numpy.sortkind= picks the algorithm — quicksort, mergesort, heapsort, stable. argsort returns the permutation instead of the data, which is what you want when sorting one array by another.
SortedContainersNot a faster sort — it never sorts. The collection is ordered at all times, so inserts are O(log n) and you get bisect and index access for free.
polarsMulti-column, lazy, and out-of-core. Sorts data larger than memory, which the others simply cannot do.
radix / countingNon-comparison sorts: O(n) for bounded integers, beating the O(n log n) floor by not comparing at all. Narrow, and unbeatable where they apply.

The point

Nothing here says stop using sorted(). It says the default has conditions attached, and knowing them is the difference between a choice and a habit. That is what a survey is for: not a winner, but the conditions under which each option wins.
